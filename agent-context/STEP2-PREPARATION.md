# 2번 실행 순서 준비 기록

`BACKEND_QUALITY_REVIEW.md` 20절의 2번은 1번 테스트 기반 위에서 신청 흐름과
수락·거절 동시성을 다룬다. 이 문서는 읽기 전용 DDD·테스트 에이전트의 준비 결과이며,
미확정 정책을 구현 승인으로 간주하지 않는다. 결정 상태의 기준은 `DECISIONS.md`와
`STATE.json`이다.

## 현재 근거와 확정 규칙

- 요구사항 PDF 3쪽은 거절 후 재요청 허용과 거절 시 받은 요청 데이터 삭제를 명시한다.
  PDF는 Git에서 제외한다.
- 자기 자신에게 신청할 수 없고, 수신자만 대기 요청을 수락·거절한다.
- 같은 사용자 쌍의 활성 관계는 하나이며, 수락 후 양측의 친구 수는 각각 10,000명을
  넘지 않아야 한다. 같은 요청의 경쟁 처리는 성공 한 번과 원자적 실패를 보장해야 한다.
- 현재 `FriendServiceImpl.requestFriend()`는 관계가 있으면 먼저 예외를 던져
  거절 후 재신청 분기가 도달 불가능하다. 수락·거절은 일반 COUNT 후 변경하므로
  같은 요청 및 공유 사용자의 서로 다른 요청 경쟁을 보호하지 못한다.
- 현재 관계의 DB 유일 키는 `(requester_id, receiver_id)` 방향별이다. 신청 Facade의
  Redis 잠금은 트랜잭션 커밋 이전에 임대가 만료될 수 있다.

## 사용자 답변과 남은 계약

| 결정 | 확정 내용 또는 남은 질문 | 영향 |
|---|---|---|
| S2-001 | 사용자는 거절 행 재사용을 잠정 제안했다. PDF의 삭제 문구, 같은 방향 신청 ID, 기존 거절 데이터 처리는 2번 설계 때 확정한다. | 관계 엔티티·저장소·신청/거절 동작·이전 요청 ID |
| S2-002 | 거절 후 B→A 신청도 허용하며 기존 A→B 요청을 재활용하지 않고 새 요청을 만든다. | 쌍 식별·중복 제약·권한·테스트 |
| S2-003 | Redis TTL 또는 장애 시 DB 제약으로 진행한다. 현재 방향별 유일 키와 일반 COUNT만으로 필요한 모든 제약이 보장된다고 가정하지 않는다. | Facade·락·DB 제약·테스트 |
| S2-003-ERROR | DB 대체 처리까지 실패할 때의 공개 오류 응답은 2번 단계에서 결정한다. | 서비스·API 테스트 |

기존 완료 요청의 재호출은 현재 `REQUEST_STATUS_ERROR`다. 이 외부 동작을 바꾸는
제안이 나오면 별도 질문을 한다. 기존 거절 데이터의 실제 변환·삭제 범위도 S2-001
답변만으로 불명확하면 추가 질문한 뒤 진행한다.

## 답변에 독립적인 구현·검증 준비

- 단일 요청의 중복/수락·거절 경합과 공유 사용자에 걸친 상한을 구분한다. 사용자
  ID 순서로 DB 행을 잠그고 관계 상태를 잠금 안에서 다시 확인하는 방안을 후보로
  검토한다. 잠금 대상·트랜잭션 범위는 답변 후 확정한다.
- 테스트는 동일 방향 중복 신청 1건 유지, 이미 수락된 관계의 새 신청 거부,
  같은 요청의 동시 수락·수락/거절 경쟁에서 성공 최대 1회와 최종 상태 일치,
  공유 사용자 9,999명에 서로 다른 요청 2건을 동시 수락할 때 최종 10,000명 이하와
  패자 요청의 부분 반영 없음으로 구성한다.
- 대량 fixture는 테스트 전용 JDBC bulk insert로 별도 커밋하고, 기존
  `IntegrationTestSupport`의 PostgreSQL/Redis 격리를 이용한다. 동시성 테스트는
  준비/시작 latch, 제한시간, 모든 예외 수집, `finally`의 executor 종료,
  별도 트랜잭션의 최종 DB 조회를 포함한다.
- 역방향 새 신청은 S2-002 답변을 적용한다. 같은 방향의 요청 ID 수명과 DB 대체
  처리 실패 응답은 S2-001·S2-003-ERROR 답변 전 임의로 정하지 않는다.
