# 사용자 결정 기록

업무 의미·공개 계약·데이터·범위·게시처럼 사용자에게 귀속되는 선택은 질문과 답변을
기록한다. 에이전트는 답변 전 기본값이나 추측으로 의존 작업을 진행하지 않는다.
`STATE.json.pendingDecisions`가 실행 차단 상태의 기계 판독 기준이다.

| ID | 질문·선택 | 사용자 답변 | 영향 범위 | 상태 |
|---|---|---|---|---|
| PDF-001 | 기존 `기능요구사항.pdf`를 Git에 포함할지 | “기능요구사항 pdf는 git에 제외해” | 모든 커밋·푸시; `.gitignore`의 `/기능요구사항.pdf` | 2026-10-21 확정 |
| PUB-001 | 현재 1번·구성 체크포인트를 지금 독립 리뷰 후 게시할지, 1~6 완료 후 한 번에 게시할지 | “일단 현재 브렌치에 1번사항에 대해서만 커밋 푸시 진행” | `setup-checkpoint`의 commit/push 시점 | 2026-10-22 확정 |
| S2-001 | PDF의 거절 요청 삭제·재신청 요구와 현재 `REJECTED` 행 보존 충돌: 거절 행·요청 ID·기존 데이터 처리 방식 | “1-A, 2-A” — 같은 방향 재신청은 해당 `REJECTED` 행의 상태를 변경해 기존 요청 ID로 재사용한다. 기존 거절 행을 일괄 삭제·이관하지 않으며 재신청되지 않은 행은 그대로 둔다. 이 범위에서는 PDF의 삭제 문구보다 사용자 결정을 우선한다. | 2번 신청·거절·저장소·데이터, `full-refactor` | 2026-10-22 확정·구현 대기 |
| S2-002 | A→B 거절 후 A→B만 재신청할지, B→A도 허용할지 | “b->a 도 허용 ... 기존 요청을 재활용하는게 아니라 ... 새로운 요청을 생성” | 2번 관계 식별·중복 방지·테스트, `full-refactor` | 2026-10-22 확정·구현 대기 |
| S2-003 | Redis TTL·장애에서 처리 방침 | “TTL, REDIS 장애 시 DB 제약으로 진행” — DB 제약의 충분성은 2번 구현에서 검증·보완 | 2번 잠금·DB 제약·테스트, `full-refactor` | 2026-10-22 확정·구현 대기 |

| S2-004 | Redis 장애 중 로컬 요청 제한기 10,000 사용자 슬롯이 모두 찼을 때 신규 사용자 ID를 HTTP 429로 차단할지 DB 처리로 통과시킬지 | 답변 대기. 현재 미등록 ID는 추적되지 않아 반복 요청을 제한 없이 통과시킨다. | 2번 요청 횟수 제한·테스트 | 2026-10-23 미결정 |

| S2-007 | 거절 행 재신청의 신청 시각 | 기존 요청 ID를 재사용하되 다시 신청한 시각을 오늘 신청으로 표시한다. | 2번 신청 목록·응답·정렬 | 2026-10-22 확정 |
| S2-008 | 기존 활성 중복 데이터가 제약 적용을 막는 경우 | 자동 삭제·병합하지 않고 별도 사용자 결정을 받는다. 현재 로컬 개발 DB의 friendship은 0행이다. | 2번 DB 제약 적용·데이터 | 2026-10-22 확정 |

후속 단계의 미확정 정책이 나타나면 여기와 `STATE.json`에 ID·질문·영향 단계를
추가한다. 사용자 답변을 받은 뒤 원문 취지·날짜·결정 근거를 기록하고 의존 작업을 재개한다.
