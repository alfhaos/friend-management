# 단계별 리팩토링 계획

기준: `BACKEND_QUALITY_REVIEW.md` 20절. **1~6번은 전용 브랜치에 게시됐다.** 아래 표는 단계별 계약이며
완료 보고가 아니다. 상태의 기계 판독 기준은 `STATE.json`, 근거는 실제 검증/리뷰 기록이다.

경로는 `src/main/java/com/apr/aprbackendassignment/`를 기준으로 적는다. 소유권은 단계가
시작될 때 실제 파일 목록으로 확정하며 한 파일을 여러 구현 에이전트에 동시에 맡기지 않는다.

단계 2와 3은 필요한 작은 계약 변경만 묶을 수 있다. 이 경우 두 단계의 완료 기준을
각각 증명한다. 패키지 이동부터 시작하지 않는다. API 공개 계약 변경은 별도 근거와
명시적인 계약 합의가 있을 때만 수행하고, 단순 내부 리팩토링으로 응답을 바꾸지 않는다.

## 1번 기존 증거와 아직 검증하지 않은 규칙

리뷰 문서 21절은 독립 PostgreSQL 16·Redis 7.4.2 Testcontainers, `IntegrationTestSupport`,
`FriendshipFixture`, 고정 개발 ID/`@Rollback(false)` 의존 제거와 샘플 생성기 분리를 기록한다.
이전 실행에서 `test sampleDataClasses`, `clean test sampleDataClasses` 각각 17건 통과와
요청 제한 메서드 단독 실행이 성공했다. 이번 설정 변경 이후 검증은 별도로 실행한다.

수락/거절 경쟁, 친구 수 상한 경쟁, 재신청, 시간 경계·기본 1초 제한 창의 만료는 후속 범위다.
기존 `createdTime` 기반 정렬 테스트는 실제 수락 시각의 근거가 아니었다. 3번에서는
신청 순서와 수락 순서를 반대로 만든 PostgreSQL fixture로 `approvedAt` 응답과 정렬을
검증했다. 해당 검증의 실행 결과는 `STATE.json`에 기록한다.

## DDD 책임과 과설계 방지

- `Friendship`: 자기 신청·수신자 권한·허용 상태 전이와 관계 수명주기.
- 작은 정책/규칙: 두 사용자의 친구 수 상한. 여러 관계에 걸친 규칙이라 관계 한 행의
  잠금만으로 동시 상한을 보장했다고 판단하지 않는다.
- 애플리케이션 서비스: 사용자/관계 조회, 잠금 대상과 순서, 커밋 범위, 유스케이스 조정.
- API 경계: 파싱·입력 검증·업무 오류의 HTTP 표현. repository가 HTTP 상태를 정하지 않는다.
- JPA 엔티티를 도메인 모델로 유지해도 된다. 순수 모델 일대일 복제·단순 전달 저장소 래퍼·
  이벤트 소싱·마이크로서비스·별도 읽기 DB를 추가할 근거는 현재 없다.
- 사용자 행 잠금은 일관성 전략이며 모든 관계를 Users 애그리거트 안으로 옮길 근거가 아니다.
- 성능·SQL 수·운영 보장 수치는 실제 측정과 실행 근거 없이 주장하지 않는다.

## 2번 실행 계획 — 신청 제어 흐름과 동시성

2번은 신청·재신청의 도달 가능한 흐름을 정리하고, 신청·수락·거절의 동시 처리에서
중복 관계와 친구 수 상한 위반을 막는 작업이다. 3번의 업무 시각·엔티티 전이 정리와
5번의 일반적인 쿼리·설정 정리는 이 단계의 정확성에 필요한 범위를 제외하고 미룬다.

1. **확정 계약과 승인 게이트:** S2-001에 따라 같은 방향 재신청은 해당 `REJECTED`
   행의 상태를 변경해 기존 요청 ID로 재사용하고, 거절 데이터는 일괄 삭제·이관하지 않는다. S2-002에
   따른 반대 방향 재신청은 새 요청을 생성한다. S2-003에 따라 Redis 장애·TTL 만료 때도
   DB가 일관성을 지켜야 한다. S2-003-ERROR에 따라 DB 제약 충돌은 HTTP 409,
   DB 자체 장애는 HTTP 503과 각각 별도 오류 코드로 응답한다. 정확한 코드·메시지
   문자열과 프로덕션 파일의 목적·대상·예상 동작을 제시해 사용자 승인을 받은 뒤 구현한다.
2. **행위·저장 계약:** 자기 신청, 중복 신청, 거절 이력, 활성 요청, 수락된 관계의
   우선순위와 허용 상태 전이를 표로 정한다. 거절 이력과 새 역방향 요청이 공존할 수
   있으므로 양방향 전체 상태를 단일 행으로 받는 `checkExistingRequest`의 의미를
   다시 정의한다. 방향별 유니크 제약만으로 양방향 중복을 막을 수 없으므로 실제
   PostgreSQL 제약과 잠금 규약을 함께 검증한다.
3. **트랜잭션·잠금 계약:** 두 참여 사용자 행을 ID 순서로 잠그는 방안을 기준으로,
   잠금 후 관계·권한·상태를 다시 조회한다. 수락 시 두 사용자의 친구 수를 같은
   트랜잭션 안에서 검사하고, 신청·수락·거절 변경이 커밋될 때까지 잠금을 유지한다.
   Redis 잠금의 lease 만료·장애가 DB 규칙을 우회하지 않게 하고, 잠금 실패·제약 충돌
   뒤에는 부분 반영이 없어야 한다. 정확한 제약·오류 처리는 결정과 테스트로 확정한다.
4. **검증 시나리오:** 같은 방향 재신청에서 해당 행·UUID를 재사용하고 재신청되지
   않은 기존 거절 행은 유지되는지 확인한다. A→B 거절 후 B→A 새 UUID 신청과 과거 이력, 중복 신청 차단,
   동일 요청의 수락/거절·중복 수락 경쟁, 공통 사용자가 포함된 서로 다른 요청의 동시
   수락과 양쪽 친구 수 상한, Redis 장애·TTL 만료, 롤백을 독립 트랜잭션의 PostgreSQL
   통합 테스트로 확인한다. 경쟁 테스트는 시작 신호·제한 시간·모든 결과 수집과
   executor 정리를 포함한다. DB 제약 충돌의 409와 DB 장애의 503 응답을 별도로
   검증하고 기존 목록·권한·요청 제한 회귀도 유지한다.
5. **구현·완료 순서:** 테스트 시나리오 확정 → 승인된 서비스·repository·잠금 코드
   수정 → 단독 테스트와 `.\gradlew.bat lint test sampleDataClasses --rerun-tasks --no-build-cache`
   실행 → 코드·보안 독립 리뷰 → 지적 수정과 재검증이다. 각 단계의
   실제 명령·exit code·대상 tree를 기록한다. 수정 필요 0건과 모든 2번 완료 기준의
   실행 증거가 있어야 2번을 완료로 표시한다.

## 단계별 반환물

오케스트레이터는 단계마다 확정 계약, 소유 파일, 변경 요약, 테스트 명령/exit code,
리뷰 지적과 해소 증거, 남은 범위를 기록한다. 리뷰 지적의 기본 필드는
`ID / 심각도 / 파일·위치 / 재현·근거 / 기대 규칙 / 담당 / 재검증 / 상태`다.
설계 불명확은 DDD, 구현 결함은 backend, 검증 부족은 test, 검사 도구는 품질 담당으로
돌려보내고 독립 리뷰를 다시 받는다. 전체 게시 규칙은 `WORKFLOW.md`를 따른다.
