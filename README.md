# apr-backend-assignment
에이피알 백엔드 과제 전형


## 사용자 기준 처리

본 과제는 사용자 인증 기능이 없으므로  
테스트를 위해 userId = 1L을 로그인 사용자로 가정하여 구현했습니다.


## 레이어 엔티티 관리
- repository: DB와 직접적으로 상호작용하는 레이어로 엔티티에 대한 로직 수행이후 엔티티를 반환 합니다.
- service: 비즈니스 로직을 처리하는 레이어로 repository에서 반환된 앤타타룰 가공하여 컨트롤러에 DTO 형태로 반환합니다.
- controller: 클라이언트 요청을 처리하는 레이어로 service에서 반환된 DTO를 응답으로 반환합니다.

## 기능요구 사항
1. 친구목록 조회 API
   - friendShip 테이블에서 requester/receiver가 현재 사용자인 목록을 조회 이후 fromEntityPage 함수를 통해 친구 아이디를 추출하여 응답으로 반환합니다.
   - 상태가 ACCEPTED인 친구 관계만 조회합니다.
   - 서비스 레이어에서 나(사용자) 아이디를 1L로 가정하여 처리합니다.
2. 받은 친구 신청 목록 조회
    - friendShip 테이블에서 receiver가 현재 사용자인 목록을 조회 이후 fromEntityPage 함수를 통해 친구 신청자 아이디를 추출하여 응답으로 반환합니다.
    - 상태가 REQUEST인 친구 요청만 조회합니다.
    - 서비스 레이어에서 나(사용자) 아이디를 1L로 가정하여 처리합니다.

3. 친구 신청 API
    - 데이터 무결성: (requester_id, receiver_id) 복합 유니크 인덱스를 통해 중복 신청을 방지하며, 신청 전 상호 관계(이미 친구인지, 이미 신청했는지)를 검증합니다.
    - 방향성: A → B 단방향으로 구성하여 신청자와 수신자의 권한을 명확히 구분합니다.
      - (동시성 문제) H2 환경 특성상 (A,B)/(B,A) 중복을 DB UNIQUE 제약으로 표현하기 어려워 서비스 레이어에서 차단했으며, 실서비스 DB에서는 함수 기반 인덱스 또는 정규화 컬럼을 통한 DB 제약으로 확장 가능합니다.
4. 친구 수락
    - 상태 변경: requester가 신청자이고 receiver가 현재 사용자인 데이터를 찾아 상태를 ACCEPTED로 변경합니다.
    - 친구 관계는 논리적으로는 양방향(A ↔ B)이지만,  
      본 과제에서는 데이터 복잡도 및 저장 공간 증가를 고려하여  
      단일 레코드 기반의 단방향 저장 구조를 유지하고  
      조회 시에만 양방향 관계로 해석하도록 설계하였습니다.
